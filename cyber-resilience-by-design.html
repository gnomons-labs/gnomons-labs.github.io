A quick definition

Cyber resilience is a property of the device itself: whether it keeps working safely, keeps its data protected, and recovers cleanly when something goes wrong — including when someone is actively trying to break it. It's engineered in at design time, not bolted on afterward.

That's different from cyber security services — audits, penetration testing, monitoring, incident response — which typically examine a product after it already exists. Our place in that picture is earlier: as your firmware engineering partner, we design and build the product itself, so resilience is part of its architecture from day one.

EN 303 645 alignment is becoming a market-access requirement, not a nice-to-have. In Japan, JC-STAR — the METI/IPA IoT security labeling scheme launched in 2025 — builds its graded, 1-to-4-star conformity requirements directly on EN 303 645. In the EU, meeting it gives manufacturers a presumption of conformity with the Cyber Resilience Act's essential requirements, the strongest alignment of any existing standard. Getting there takes more than choosing a chip with the right security features; it takes an engineering team that turns those features into protections built into your product's actual firmware, from day one. That's the discipline behind everything on this page.

built EN 303 645 · Secure storage

Data stays protected, even if the application is compromised

Keys, credentials, and other sensitive data live where ordinary application firmware simply cannot reach — buggy or compromised code cannot expose them. Any attempt to bypass the boundary is caught by the processor's own security hardware, which safely halts and resets the device rather than continuing in an unsafe state.

Reduces breach impact to the boundary, not the whole device
Hardware-checked memory access, automatic reset on violation, AES-encrypted external flash.
Delivered as
On-chip secure storage Flash encryption
built EN 303 645 · Attack surface

A minimized attack surface, built in from the start

Sensitive peripherals are owned exclusively by a protected core; application code gets only a narrow, deliberate set of permitted operations — never direct hardware access. We built this pattern against multiple independent peripheral types, not just once.

A repeatable design pattern, not a one-off demo
Verified down to zero non-secure interrupts on the isolated peripherals.

built EN 303 645 · Software integrity

Firmware that verifies itself before it ever runs

A protected bootloader — never the application — is the sole authority over whether a firmware image is allowed to run: it cryptographically verifies the image's signature before booting it. If a violation is triggered at run time anyway, the device detects and safely contains it too.

Verified at boot, contained at run time — both halves covered
ECDSA-P256 signature over SHA-256, checked by the on-chip crypto engine before every boot.
Delivered as
Secure bootloader Run-time fault handler Boot-integrity counter
